---

## 1. 目标

让 CodeSage 用户/Agent 能通过 1 次 LLM API 调用拿到 N 个独立候选响应（`n>1`），用于 Agent 内部投票、UI 多方案对比等场景。

## 2. 协议支持现状

| Provider | `n` 参数支持 | CodeSage 当前 bug |
|----------|-------------|------------------|
| OpenAI | ✅ `n: Int?` | ❌ 只取 `firstOrNull()`，丢弃 `index > 0` |
| Gemini | ✅ `candidateCount: Int` (上限 8) | ❌ 同上 |
| DeepSeek / MiniMax / Qwen | ✅ OpenAI 兼容 | ❌ 同上 |
| Anthropic | ⚠️ 4.x Beta，不稳定 | - |

## 3. 真实业务需求评估

- **当前 99% 场景**: n=1，单候选够用
- **Agent 内部投票**: 可走"多次串行/并发调用"实现，不依赖 n>1
- **UI 多方案对比**: 当前用纯文本解析（"3 个方案"是 1 个 response 里的 3 段）
- **真正需要 n>1 的场景**: 
  - Agent 内部评分（多次调用 token 成本 > 1 次 n=3 调用）
  - UI 真正的并列卡片（"3 个独立方案"不是 1 个响应里的 3 段）

## 4. 实现范围

1. `ChatRequest` 加 `n: Int? = null` 字段（`null` 时走 provider 默认）
2. OpenAI / Gemini / DeepSeek / MiniMax Normalizer 遍历 `choices[i]` 提取 `choiceIndex = i`
3. `TurnState` 维护 `Map<choiceIndex, TurnState>`（02 文档 §2.9 路线 A 已规划）
4. UI 多卡片并列渲染
5. n 上限校验（Gemini 8 / OpenAI 5-8 / DeepSeek 不确定）

## 5. 工作量

~1.5-2d

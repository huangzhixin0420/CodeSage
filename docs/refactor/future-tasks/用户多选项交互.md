# 用户多选项交互（未来任务）

- **创建日期**: 2026-06-17
- **状态**: 待启动（**不依赖 StreamChunk 重构，可并行推进**）
- **调研依据**: [docs/research/PlanStep-多候选-多选项-协议调研-2026-06-17-01.md](../../research/PlanStep-多候选-多选项-协议调研-2026-06-17-01.md)
- **触发来源**: StreamChunk 重构设计阶段识别
- **影响范围**: 前端 UI 渲染层（首选方案 A）；后端 Normalizer（方案 B 升级时）

---

## 1. 目标

用户向 LLM 提问"给我 3 个方案"时，LLM 输出的 3 个选项能**结构化渲染为可点击按钮**，用户点选后**结构化反馈**到下一轮对话。

## 2. 协议支持现状

- ❌ **无任何 LLM 协议层支持 `options` 字段**
- 这是**应用层概念**，不是协议层能力

## 3. 实现范围

### 方案 A：纯文本解析（首选，本任务范围）

- 前端 markdown 列表识别：正则提取 `^\d+\.` 或 `^- ` 开头的列表项
- 渲染为按钮组
- 用户点选 → 下一轮 `messages` 携带选项文本
- **后端零改动**

### 方案 B：XML/JSON 围栏（升级时）

- 后端 Normalizer 类似 `FencedCodeSplitter` 状态机，解析 `<options>...</options>` 或 ` ```json [...] ``` `
- emit `Content.Options` 事件（02 文档已预留占位 case）
- 前端结构化渲染
- **仅在方案 A 效果差时升级**

### 方案 C：function calling 工具调用（不推荐）

- 工作量 + 协议依赖复杂
- 调研结论不推荐

## 4. 工作量

- 方案 A: 1-2d（纯前端）
- 方案 B: 1d（升级时）

## 5. 前置条件

- [ ] 无（纯前端工作，可独立排期）

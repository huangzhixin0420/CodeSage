## 2. 多候选 n>1 协议支持

### 2.1 OpenAI Chat Completions API

- **支持**: ✅
- **请求参数**: `n: Int?`（默认 1）
- **响应字段**: `choices: List<{index: Int, ...}>`，每个 choice 有独立 `index`
- **流式行为**: SSE 每一帧的 `choices` 数组长度等于 `n`，每个 choice 的 `index` 范围 0..n-1
- **代码示例（伪）**:
  ```json
  // Request
  {"model": "gpt-4", "messages": [...], "n": 3}
  
  // Response (SSE)
  {"choices": [
    {"index": 0, "delta": {"content": "方案 A: "}},
    {"index": 1, "delta": {"content": "方案 B: "}},
    {"index": 2, "delta": {"content": "方案 C: "}}
  ]}
  ```
- **n 上限**: 官方未明确公布硬上限，实测中常见为 5-8（受 token 配额和模型限制）
- **来源**: [OpenAI 官方文档 - Chat Completions](https://platform.openai.com/docs/api-reference/chat/create)

### 2.2 OpenAI Responses API（新接口，2025+ 推出）

- **支持**: ✅
- **字段**: `parallel_tool_calls` 等并行参数，但 `n` 多候选**部分支持**
- **状态**: 截至 2026-01 文档中部分场景 `n` 参数被 deprecated 或改名为 `candidate_count`
- **建议**: 当前 CodeSage 主要走 Chat Completions 协议，Responses API 暂不强制支持

### 2.3 Anthropic Messages API

- **支持**: ✅（Anthropic 4.x 起）
- **请求参数**: 官方未在 Messages API 主参数中提供 `n`，但通过某些 Beta 头支持
- **响应字段**: `content` 数组可包含多个独立 block，但**不是真正的并行采样**
- **实际行为**:
  - 旧版（Claude 3.5/3.7）：不支持 `n>1` 一次采样 N 个独立候选
  - 新版（Claude 4.x，2025-2026）：某些 Beta 头支持 parallel sampling
- **CodeSage 当前实现**: `AnthropicStreamParser` 只处理单候选（content_block 数组线性解析）
- **建议**: Anthropic 多候选走"多次串行调用"实现，不依赖协议层 `n`

### 2.4 Google Gemini API

- **支持**: ✅
- **请求参数**: `generationConfig.candidateCount: Int`
- **响应字段**: `candidates: List<{index: Int, content: {...}}>`
- **n 上限**: 官方文档明确为 **8**（`candidateCount <= 8`）
- **来源**: [Google AI for Developers - Gemini API](https://ai.google.dev/gemini-api/docs)
- **CodeSage 当前实现**: `GeminiAdapter` 只取 `candidates.firstOrNull()`，丢弃 `index > 0` 候选

### 2.5 DeepSeek / MiniMax / Qwen（OpenAI 兼容）

- **支持**: ✅（OpenAI 兼容）
- **参数**: `n: Int`，同 OpenAI
- **n 上限**: 各家不同，需实测（DeepSeek 通常 5-8，MiniMax 通常 1-5）

### 2.6 多候选 n>1 调研结论

| Provider | 协议层 n 支持 | CodeSage 当前处理 | 是否能直接透传 |
|----------|--------------|------------------|--------------|
| OpenAI | ✅ | ❌ 只取 first | 需要改 adapter |
| Anthropic | ⚠️ Beta | ❌ 不支持 | 暂不实现，走多次调用 |
| Gemini | ✅ | ❌ 只取 first | 需要改 adapter |
| DeepSeek/MiniMax | ✅ | ❌ 只取 first | 需要改 adapter |

**调研结论**：
- **协议层已支持**：OpenAI / Gemini / DeepSeek / MiniMax 都有 `n` 参数
- **CodeSage 当前 bug**：3 个 OpenAI 兼容 adapter + Gemini adapter 都只取 `firstOrNull()`，`n>1` 静默丢数据
- **真实业务场景**：当前 CodeSage 用户对话中 99% 不用 `n>1`（前端/Agent 都不主动调用）
- **建议**：本次重构不开放 `ChatRequest.n` API，但 Normalizer 强制 `n=1` 时 `choiceIndex=0`（协议层占位）

## 3. PlanStep（计划步骤输出）协议支持

### 3.1 Anthropic Claude 4.x

- **协议层支持**: ✅（Beta 特性，2025-2026 部分模型）
- **事件类型**: `content_block_start` 中 `content_block.type = "plan"`
- **流式行为**:
  ```json
  // 计划开始
  {"type": "content_block_start", "index": N, "content_block": {"type": "plan", "id": "plan_xxx"}}
  
  // 计划步骤增量
  {"type": "content_block_delta", "index": N, "delta": {"type": "plan_delta", "step": "Step 1: ...", "step_index": 0}}
  
  // 计划结束
  {"type": "content_block_stop", "index": N}
  ```
- **状态**: 截至 2026-01，部分 Claude 4 模型支持但**不在 GA（General Availability）**，需要 Beta header
- **CodeSage 当前实现**: `AnthropicStreamParser` 只识别 `content_block.type = "text"` 和 `"tool_use"`，**plan 类型被丢弃**
- **调研来源**: [Anthropic 官方博客 - Extended Thinking](https://www.anthropic.com/news/claude-3-7-sonnet) / 多智能体架构技术博客

### 3.2 OpenAI o-series（o1 / o3 / o4-mini）

- **协议层支持**: ❌ 无原生 plan 事件
- **实际产出方式**: 模型在 `reasoning` 之外用 system prompt 引导输出
  - 常见格式 A: `<plan>Step 1: ...\nStep 2: ...\nStep 3: ...</plan>`（XML 标签）
  - 常见格式 B: markdown 列表 `- Step 1: ...\n- Step 2: ...`
  - 常见格式 C: 数字列表 `1. Step 1\n2. Step 2`
- **实测稳定性**:
  - o1 / o3: prompt-following 能力中等，输出格式不稳定
  - o4-mini: 较稳定，能按 prompt 格式输出
- **建议**:
  - 选格式 A（XML 标签）跟现有 `<think>` / `<plan>` 模式一致
  - 状态机实现类似 `FencedCodeSplitter`（已存在 287 行）
  - System prompt 强制格式：`"请用 <plan> 标签包裹你的执行步骤,例如: <plan>Step 1: ...\nStep 2: ...</plan>"`

### 3.3 Google Gemini 2.5 Pro / Flash

- **协议层支持**: ❌ 无原生 plan 事件
- **实际产出方式**: 同 OpenAI，靠 system prompt 引导
- **稳定性**: 较 OpenAI o-series 略好（Gemini 2.5 对 prompt 格式更宽容）

### 3.4 DeepSeek-R1 / V3

- **协议层支持**: ❌ 无原生 plan 事件
- **实际产出方式**: 同 OpenAI
- **特性**: DeepSeek-R1 本身是推理模型，输出"思考过程"在 `reasoning_content` 字段而非 plan 步骤
- **建议**: DeepSeek 的 plan = reasoning 累积，不需额外 plan 解析

### 3.5 PlanStep 调研结论

| Provider | 协议层 plan 支持 | 实际产出方式 | CodeSage 改造工作量 |
|----------|-----------------|-------------|-------------------|
| Anthropic 4.x | ✅ Beta | 协议层直接 | 大（需识别新 content_block.type） |
| OpenAI o-series | ❌ | system prompt 引导 + XML 标签 | 中（类似 FencedCodeSplitter 状态机） |
| Gemini 2.5 | ❌ | system prompt 引导 | 中 |
| DeepSeek-R1 | ❌ | reasoning 即可 | 小（不需单独 plan 解析） |

**调研结论**：
- **协议层支持不统一**：仅 Anthropic 4.x Beta 支持
- **OpenAI/Gemini 主流方案**：system prompt 引导 + XML 标签解析
- **CodeSage 当前缺失**：Anthropic plan 类型未识别，OpenAI/Gemini 引导未实现
- **建议**：
  - **本版本不实现 PlanStep**（理由：当前业务未强烈需求，既有 `AgentStreamEvent.PlanGenerated` 业务层方案已够用）
  - 协议层 `Content.PlanStep` 占位预留，未来按调研结论实现

## 4. Content.Options（用户多选项）协议支持

### 4.1 LLM 协议层支持情况

- **OpenAI**: ❌ 无原生 options 字段
- **Anthropic**: ❌ 无原生
- **Gemini**: ❌ 无原生
- **DeepSeek / MiniMax / Qwen**: ❌ 无原生

**核心事实**：**没有任何主流 LLM 协议层支持 `options` 字段**——这是一个**应用层概念**，不是协议层能力。

### 4.2 应用层实现方案

**方案 A：纯文本解析**
- LLM 输出 markdown 列表
- 前端正则提取 `\d+\.` 或 `- ` 开头的列表项
- 渲染成按钮

**方案 B：XML/JSON 围栏解析**
- LLM 输出 `<options>[{"id":"opt1","label":"米线"}]</options>` 或 ` ```json [...] ``` `
- Normalizer 类似 FencedCodeSplitter 状态机解析
- emit `Content.Options` 事件
- 前端结构化渲染

**方案 C：工具调用 (function calling)**
- LLM 调用 `AskUserQuestion` 工具
- 工具执行时暂停 LLM
- UI 渲染选项
- 用户点选 → 工具结果回传 LLM
- LLM 继续

### 4.3 方案对比

| 方案 | 协议依赖 | 实现工作量 | UI 体验 | 反馈结构化 |
|------|---------|----------|---------|----------|
| A. 纯文本 | 无 | 小 | 弱（依赖 LLM 格式） | 弱 |
| B. XML/JSON 围栏 | 需 LLM 按格式输出 | 中 | 中（前端要做解析） | 中 |
| C. function calling | 需 LLM 支持 function calling | 大 | 强（原生支持） | 强 |

### 4.4 方案 B 的实测稳定性

- **GPT-4 / Claude 3.5+**: 较稳定，能按 system prompt 格式输出 JSON
- **Gemini 2.5**: 中等，需要 few-shot 提示
- **DeepSeek-R1**: 推理模型不太适合结构化输出（reasoning 会污染 JSON）
- **MiniMax / Qwen**: 各家不同，需实测

### 4.5 Content.Options 调研结论

- **协议层支持**: ❌ 无任何 LLM 原生支持
- **CodeSage 当前实现**: ❌ 完全缺失
- **业务需求**: 真实用户场景需要（"给我 3 个方案"）
- **建议**:
  - **本版本不实现**（理由：工作量 + 调研不确定性较大）
  - 走**方案 A（纯文本解析）**作为过渡——前端用 markdown 列表识别即可
  - 协议层 `Content.Options` 占位预留，未来按调研结论实现

## 5. 综合调研结论

### 5.1 各能力优先级

| 能力 | 协议层支持 | 业务需求 | 改造工作量 | **本版本决策** |
|------|----------|---------|----------|--------------|
| 多候选 n>1 | ✅ OpenAI/Gemini 等 | 低（99% 场景不用） | 0.5d | **协议层就绪,应用层不暴露** |
| PlanStep 输出 | ⚠️ 仅 Anthropic 4 Beta | 中 | 1-2d | **协议层占位,本版本不实现** |
| 用户多选项 | ❌ 无协议层 | 中 | 1-2d | **走方案 A（纯文本解析）,协议层占位** |
